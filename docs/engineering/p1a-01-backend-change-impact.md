# P1A-01 backend change-impact record

- Changed capabilities/modules in this candidate: Leads query/orchestration/contracts/presentation HTTP and Identity Review contracts/read participants; thin app routes, manifests/registry, evidence, and tests. Contacts, Companies, and Platform authorization/database/idempotency/Audit/Outbox remain unchanged public dependencies reused by the new reads.
- Changed public contracts: `LeadInquiryIntakeCommandV1`, `LeadInquiryIntakeResultV1`, protected `lead-identity-review-detail.v1`, authorized `lead-identity-review-queue.v1`, and discriminated versioned identity-review Hold/Resolve decision/result V1. The presentation addendum freezes canonical responsibility names, masked fields, server capabilities, stable errors/reconciliation, nullable decision IDs, and `nextView`. No schema contract changed.
- Changed routes/pages: Lead POST remains the canonical manual command adapter. Lead collection/detail GET now call strict `listLeadSummaries.v1` and `getLeadDetail.v1` public queries with tenant-safe errors and private/no-store headers. The canonical detail capability is read-only and does not expose the legacy PATCH/editor model. No page or frontend code changed.
- Changed commands/queries: `submitLeadInquiryV1`, `getIdentityReviewDetailV1` (compatibility alias `getIdentityReviewCandidatesV1`), `listIdentityReviewQueueV1`, and `decideLeadIdentityReviewV1` (compatibility alias `resolveLeadIdentityReviewV1`). Leads composes owner participants and current authorization; no cross-owner private repository imports were added.
- Ownership/dependencies verified, not reassigned: Identity Review issues SQL only for its four owned tables; Leads owns Lead/intake reads; protected queries compose Contact/Company and Platform public participants. Fast gates still reject undeclared/cross-owner SQL and private imports.
- Changed tables/migrations: none in this Dev2 correction; accepted schema ancestors are `71ee512` and `ac3bf67`, corresponding to the accepted Dev3 base. No migration, constraint, or configuration was changed.
- Changed lock/write trace: both intake and resolution interleave Company identity-key authority, all relevant Company rows in deterministic UUID order and recheck, Contact key authority, all relevant Contact rows in deterministic UUID order and exact shared-cap recheck, assignment/visibility locks, then immediate actor/permission/visibility/assignment/version/head/target/candidate revalidation. Resolution acquires no identity lock after assignment references.
- Changed candidate behavior: the private committed intake outcome retains the complete canonical query V1, including Company domain. Intake and resolution call the same email/phone/mixed-probable selection algorithm: 10 per evidence class and at most 30 protected results. Link target ID/version must equal the selected snapshot before locking and again be fresh after all locks.
- Changed Audit/events: runtime allowlists enforce operation/action/target and topic/aggregate/topic-specific payload shapes before persistence. Every command writes one governing Audit plus the exact unique required versioned event set; replay writes neither.
- Changed authorization/tenant behavior: replay remains original-actor-bound and revalidates current Workspace, User, Session, Membership, Role, assignment, visibility, and result disclosure. Protected detail/queue lock the bounded Lead/review/identity set, globally sorted page assignment/visibility references, and all mutable actor facts immediately before strict presentation. Mutation conflicts receive a final disclosure revalidation; guessed, resolved, inactive, reassigned, or hidden resources remain tenant-safe and carry no navigation. The existing 30/minute P1A limiter now uses a schema-supported persisted action with an isolated `p1a_lead_intake` risk-key namespace; limits and external error semantics are unchanged and no migration was introduced.
- Changed UI/accessibility: none; legacy create response retains `id`/`version` compatibility.
- Tests/evidence: 320/320 active fast tests; 44/44 focused P1A manual-intake/read PostgreSQL tests; 213/213 full serialized PostgreSQL tests across 22 files; production build passed. Default-planner performance at 100,001 Leads, 100,030 Contacts, 25,010 Companies, 10,001 pending reviews, and 10,030 candidate rows used 30 samples per measurement. Canonical Lead detail/list/exact-email-search p95 measured 3.721/5.262/85.465 ms. Controlled PostgreSQL evidence covers phone zero-mutation/replay, nullable reads, tenant denial, and intake/resolution overlap alongside the accepted review/rollback suite. See `p1a-01-postgresql-evidence.md`.
- UAT defect correction: pinned `libphonenumber-js` backs the authoritative `p1a-identity-v2` phone value object. It accepts the approved formatted NANP/leading-1 and explicit international forms, preserves display, stores E.164 and actual calling code, and rejects ambiguity/extensions before transaction entry. New canonical list/detail views use `display_name`, nullable Company/contact/assignment truth, source versus channel attribution, a 50-row deterministic cursor, strict masks, and public owner participants.
- Known limitations: manual only; compatibility POST accepts legacy payload with its historical CA default. Canonical Lead detail is read-only. CSV/XLSX, web/public adapters, canonical editing, drag/drop, conversion, routing, merge, frontend work, and deployment remain deferred.
- Rollback: revert the scoped Dev2 correction commit. Accepted additive schema remains in place; no destructive data rollback is required. Once P1A writes exist, preserve Lead/intake/review/Audit/outbox lineage and use forward correction rather than deleting records.
