# P1A-01 backend change-impact record

- Changed capabilities/modules: Leads, Contacts, Companies, and Identity Review; Platform authorization, database, idempotency, Audit, and Outbox ports.
- Changed public contracts: `LeadInquiryIntakeCommandV1`, `LeadInquiryIntakeResultV1`, protected candidate view V1, and discriminated versioned identity-review Hold/Resolve decision/result V1. No schema contract changed.
- Changed routes/pages: Lead POST translates legacy input into the canonical manual command and accepts V1; Lead GET/detail remain legacy-compatible; Lead identity-review GET/POST stay thin authenticated adapters. No page or frontend behavior changed.
- Changed commands/queries: `submitLeadInquiryV1`, `getIdentityReviewCandidatesV1`, and `decideLeadIdentityReviewV1` (compatibility alias `resolveLeadIdentityReviewV1`). The candidate-detail query moved to the Leads owner because it authorizes and composes Lead/intake context.
- Changed ownership/dependencies: Identity Review now issues SQL only for its four owned tables. Leads owns all Lead/intake reads and locks. Contacts issues no Company SQL. Companies exposes the explicit read-only `companyContactCandidateReadModel` for exact name+Company Contact evidence. Fast gates scan actual module SQL and reject undeclared/cross-owner tables except that reviewed read model.
- Changed tables/migrations: none in this Dev2 correction; accepted schema ancestors are `71ee512` and `ac3bf67`, corresponding to the accepted Dev3 base. No migration, constraint, or configuration was changed.
- Changed lock/write trace: both intake and resolution interleave Company identity-key authority, all relevant Company rows in deterministic UUID order and recheck, Contact key authority, all relevant Contact rows in deterministic UUID order and exact shared-cap recheck, assignment/visibility locks, then immediate actor/permission/visibility/assignment/version/head/target/candidate revalidation. Resolution acquires no identity lock after assignment references.
- Changed candidate behavior: the private committed intake outcome retains the complete canonical query V1, including Company domain. Intake and resolution call the same email/phone/mixed-probable selection algorithm: 10 per evidence class and at most 30 protected results. Link target ID/version must equal the selected snapshot before locking and again be fresh after all locks.
- Changed Audit/events: runtime allowlists enforce operation/action/target and topic/aggregate/topic-specific payload shapes before persistence. Every command writes one governing Audit plus the exact unique required versioned event set; replay writes neither.
- Changed authorization/tenant behavior: replay remains original-actor-bound and revalidates current Workspace, Membership, Role, assignment, visibility, and result disclosure. Mutation paths revalidate authority after all business and assignment locks; denials remain tenant-safe.
- Changed UI/accessibility: none; legacy create response retains `id`/`version` compatibility.
- Tests/evidence: 15/15 focused contract/module/route/security tests; 22/22 focused P1A PostgreSQL tests; 187/187 full serialized PostgreSQL tests across 21 files; representative 100k Lead/100k Contact/25k Company performance with 30 samples per measurement. Rollback covers every intake boundary, Hold Audit/outbox, every Resolve boundary/event, and same-key retry. See `p1a-01-postgresql-evidence.md`.
- Known limitations: manual only; compatibility POST accepts legacy payload; phone default is the current North American `CA` policy when no explicit CA/US override is supplied. CSV/XLSX, web/public adapters, frontend review UI, conversion, routing, merge, and deployment remain deferred.
- Rollback: revert the scoped Dev2 correction commit. Accepted additive schema remains in place; no destructive data rollback is required. Once P1A writes exist, preserve Lead/intake/review/Audit/outbox lineage and use forward correction rather than deleting records.
