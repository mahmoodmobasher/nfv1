# Leads frontend feature

Manual P1A Lead inquiry intake plus canonical list-primary Lead presentation, secondary ordered Pipeline board, read-only detail, bounded ACTIVITY-01A manual create/newest-first target list, and the bounded LEAD-CONVERSION-01 preview/confirmation flow. Public entry: `index.ts` (browser-safe); server-only entry: `server.ts`. Server loaders call only public owner-module query APIs and runtime-parse every view through strict transport schemas before rendering. The feature composes only `src/frontend/design-system` public components and server-produced stages, assignment labels, masked contact fields, capabilities, and navigation.

ACTIVITY-01A uses the accepted Activities-owned `activity-create.v1` and `lead-activity-list.v1` contracts. It renders only one `crm.lead` target, server-derived view/create capability, opaque keyset continuation, manual activity roots, and truthful replay/error reconciliation. Confirmed filters remain separate from requested filters until a successful response, rapid stale responses are discarded, and locally reconciled creates retain strict `(occurredAt, activityId)` descending order without cursor duplicates. A stale-version conflict fences submission and preserves the safe draft until an explicit authority reload succeeds. Pending, validation, conflict, replay, success, and failure feedback remain semantically distinct, with validation focus landing on the linked summary before a user follows an error link to its control. Email is record-only evidence and never implies delivery. Authority loss clears the parent protected Lead surface and all Activity content, drafts, results, cursors, and request identity. Global or multi-target timelines, Tasks, system activity, edit, archive, rescheduling, providers, and legacy `lead_activities` are outside this frontend.

CSV/XLSX, public adapters, customer creation during conversion, Delivery creation, Pipeline mutation, and the legacy Lead editor remain outside this slice.
